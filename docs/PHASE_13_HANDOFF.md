## Implementation report

1. **Canonical entitlement authority:** ReaderMembership remains the single user-level Subscription aggregate. `subscriptionService` evaluates its dates/status/paid periods; `entitlementService` provides the shared entitlement catalog. User booleans and browser state never grant access.
2. **Activation:** Verified checkout HMAC plus captured Payment/paid Order, or a verified signed capture/order webhook, invokes the same transactional lifecycle service. Stored Payment terms must match PriceCatalog. Membership, Payment attribution, Invoice association and internal audit commit together; money remains integer minor units in the original currency.
3. **Renewal:** A new term follows the latest retained paid end, preserving remaining purchases. With no remaining period, it starts at application verification time. Duration comes from the catalog; UTC calendar months clamp month-end dates. Each attributed purchase keeps its assigned dates.
4. **Expiration:** Every canonical lookup requires `start <= now < end`; no worker/cron is needed. Exact expiry denies access even when stored status still says active. Future windows/refund gaps are denied and account status reports expired/scheduled immediately.
5. **Cancellation:** Audited application cancellation preserves already-paid periods and is idempotent. Catalog Orders are prepaid and `autoRenew=false`; no provider renewal is invented. An explicit later purchase clears cancellation. Recurring provider cancellation/portal/resumption remain unavailable.
6. **Failed payments:** Failure changes the Payment and a safe account issue summary only. It cannot activate, extend, revoke existing time, or create grace. A verified recovery can capture the same order after failure; success clears issues. Existing explicit legacy grace remains supported, and already-paid time survives past-due state.
7. **Refund/revocation:** Pending, failed and partial refunds preserve access. Full processed totals remove only that Payment's attributed period in settlement's transaction and write one revocation audit. Invoice recovery preserves actual refund totals. Replays cannot refund/revoke twice.
8. **Overlapping entitlements:** Current access uses the union of valid attributed periods. Independently valid later/overlapping purchases survive refund of an older purchase. Original later dates are not shifted; a refunded stacked term can leave a denied gap until the next paid start.
9. **Premium authorization:** Article/Story serializers, contentPreview, structured bodies/sections, Premium Learn and Life use the existing canonical resolver/middleware. Integration tests deny expired access despite a forged legacy User flag. Actual Article/Story content, layouts and controllers were unchanged.
10. **Account/client behavior:** Existing Premium checkout sends product code/idempotency, waits for server verification and refreshes authoritative membership. Optional authentication selects the stored-account INR/USD price display. The existing dashboard shows start/expiry, prepaid status, payment issues and scheduled access; shared state refreshes at date boundaries/focus/visibility. Account serialization omits internal references, raw periods, provider secrets/customer/subscription IDs and webhook data.
11. **Idempotency:** Unique provider BillingEvent claims deduplicate delivery. Payment's `entitlementAppliedAt` prevents callback/webhook/order event convergence from extending twice. Internal activation/revocation audit IDs are deterministic; repeated capture preserves original financial dates/totals.
12. **Concurrency:** Real Mongo transactions serialize same/different purchase writes to one membership. Driver conflict retries and bounded first-membership uniqueness retries use fresh snapshots. Cancellation state/audit and full-refund settlement/revocation are transactional. Provider HTTP stays outside transactions; process memory never deduplicates financial effects.
13. **Event ordering:** Captured/refunded Payment states cannot roll back to failure. Failed-order issue ordering uses internal order creation time against a monotonic successful-activation boundary and latest issue attempt. Earlier requests committing later cannot lower that boundary. Unsupported subscription deliveries are ignored. Subscription transition helpers reject competing equal/older times and repeated event IDs are read-only.
14. **Schema/model changes:** ReaderMembership gains optional attributed `paidPeriods`, `latestSuccessfulPaymentAt`, and `lastPaymentIssue`. Payment gains optional applied/start/end/revoked dates. Invoice membership association can be filled during capture recovery. Legacy rows without an array retain existing access semantics and convert remaining valid access lazily; an empty array grants no paid access. No User Premium truth source or new Admin adjustment surface was added.
15. **Migration/index changes:** None required. Existing user, owner/history, provider order/payment, Invoice payment and BillingEvent replay indexes cover all operations. Optional fields require no eager backfill. Migration 013 was not changed. Production lifecycle requires Mongo transactions on a replica set/sharded topology.
